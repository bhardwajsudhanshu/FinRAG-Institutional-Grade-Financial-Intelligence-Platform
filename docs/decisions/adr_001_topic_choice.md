# ADR-001: Why SEC 10-K/10-Q Filings as the RAG Domain

**Status:** Accepted
**Date:** 2026-09-05
**Deciders:** Project lead, FinRAG

## Context

We're choosing a domain for a production-grade RAG portfolio project. The
domain needs to support a 12-week build that goes from a naive baseline to
a deployable system. The candidate domains considered:

1. **Legal case law** (court opinions, statutes)
2. **Biomedical literature** (PubMed abstracts)
3. **Customer support transcripts**
4. **SEC 10-K/10-Q filings** ← chosen
5. **Software engineering docs** (e.g. AWS, Kubernetes)

## Decision

We chose **SEC 10-K/10-Q filings + earnings call transcripts** as the RAG
domain, focused on 20 publicly-traded US companies over 3 fiscal years.

## Rationale

### 1. Real-world impact (vs. toy problems)
- A $10B+ market: hedge funds, equity research, RIAs
- A missed clause in a 10-K ("geopolitical risk", "going concern") can
  cause measurable financial loss
- "Did management change their position on X?" is a question RIAs ask
  daily and existing tools answer poorly

### 2. Right level of difficulty for a portfolio project
- **Long documents** (10-Ks are 80K–200K tokens) — exercises real
  chunking tradeoffs
- **Structured layout** (Item 1, 1A, 7, 7A, 8) — enables document-aware
  chunking
- **High-stakes recall** — forces serious evaluation (RAGAS, not vibes)
- **Cross-document reasoning** — "Compare AAPL and MSFT capex" is a real
  test of multi-doc retrieval
- **Numeric + qualitative mix** — tests whether the system can do math on
  retrieved context, not just paraphrase

### 3. Publicly available data
- EDGAR is free, well-documented, no auth required for the data itself
- Filings are HTML, easy to parse
- 3-year corpus fits in ~50M tokens, cheap to embed and re-embed

### 4. Maps to current SOTA techniques
- **Contextual retrieval** (Anthropic 2024) — financial language is highly
  context-dependent
- **Late chunking** (Jina 2024) — clauses that span Items benefit
- **RAPTOR** — "summarize Apple's risk profile over 3 years" is a real
  analyst task
- **HyDE** — financial questions are often abstract
- **CRAG** — finance has post-cutoff events (earnings, M&A) that need
  fresh context

### 5. Excellent interview talking points
- Every technique has a paper or company blog post behind it
- The "story" of how we got from naive chunking → contextual retrieval
  is a clean narrative
- The benchmark results (4 vector DBs compared) are real and publishable

## What we explicitly chose NOT to do

- **GraphRAG / entity-relation extraction** — most financial entities are
  already in XBRL, which is structured data, not text. The marginal
  value over a flat index is low.
- **Multi-modal** (10-K charts, tables) — most of the qualitative content
  is in the text. We can add this later if needed.
- **Real-time market data** — that's a different problem (low-latency
  data pipeline). Our scope is document RAG.

## Consequences

- We need to comply with EDGAR's 10 req/sec rate limit (handled in
  `data/ingest_sec.py`)
- We accept that some niche 10-Ks may not parse cleanly with our regex
  parser — we'll spot-check 5 filings and iterate
- The eval set (200 Q&A pairs) needs to be hand-curated or generated by
  a high-quality LLM (Gemini 2.5 Pro) — this is Week 2 work

## Alternatives considered

- **Legal case law**: similar structure but slower data access (CourtListener
  API is OK, but filings are paywalled for many jurisdictions). Less
  marketable as a portfolio piece.
- **Biomedical literature**: high-quality text but PubMed abstracts are
  already structured, and the "right answer" to most questions is a
  citation, not synthesis. Less interesting for a RAG system.
- **Customer support transcripts**: too narrow, no good public dataset.
- **Software docs**: LangChain/LlamaIndex already have this solved.
  Hard to add unique value.
