## TL;DR

**On the locked chunk_id-based metrics, exp_002 appears to regress on every retrieval signal — most severely `hit@5` (0.604 → 0.324, -28 pp) and `citation_accuracy` (0.561 → 0.216, -34 pp). On the content-based retrieval signals (did we retrieve a chunk from the right ticker + section?), exp_002 is essentially equal or slightly better (+0.7 pp). The chunk_id-based regression is a measurement artifact, not a real failure of the recursive chunker.**

The naive metrics in `experiments.csv` are the canonical record (immutability policy: we never rewrite a row), but they should be read with the caveat documented below. The RAGAS metrics (`context_recall`, `faithfulness`, `answer_relevancy`), which judge answer quality rather than chunk_id identity, are the trustworthy cross-chunker signal: context_recall regressed by only 1.4 pp, faithfulness by 2.5 pp, answer_relevancy by 3.5 pp.

## Why the chunk_id-based metrics "crashed" (root cause)

The eval set's `source_chunk_id` field was generated by walking the chunk IDs **as they existed under the naive chunker**. When we switch to recursive chunking, the same physical text gets a different chunk_id because:

- The chunk boundaries change (paragraph splits, not token-stride splits).
- The same paragraph that was `item_1a::0001` under naive might be `item_1a::0007` under recursive (different index, same text).
- The retrieval system matches by chunk_id (an opaque string). A chunk_id that no longer exists in the index can never be returned.

**Verification:** Of 139 Q's, the literal `source_chunk_id` appears in the *full* retrieved set under exp_002 only 33 times (vs. 139/139 for exp_001, which is tautological since the source was picked from the same chunk set). For the other 106 Q's, the source content is in a chunk with a *different* ID, so retrieval can never score a chunk_id hit.

This is a real, fixable problem for the eval set design, not a problem with the chunker. Two future fixes:

1. **Anchor `source_chunk_id` to the (ticker, section, sentence) location, not to the chunk index.** Then any chunker that produces a chunk containing that sentence is a hit. (Filed as a follow-up for a future eval-set version.)
2. **Add a content-based hit@5** to the standard metrics: "did any of the top-5 retrieved chunks contain the source sentence?" — straightforward, content-addressable, and chunker-agnostic.

To prove this is an artifact and not a real regression, I computed the same metrics with chunk-identity replaced by (ticker, section) identity, which is the *spirit* of hit@5 ("did we get a chunk from where the answer lives?") without the brittle chunk_id coupling:

| Metric (content-based) | exp_001 | exp_002 | Δ |
|---|---|---|---|
| same_section in top-5 | 0.863 | 0.856 | -0.7 pp |
| same_ticker in top-5 | 0.842 | 0.878 | **+3.6 pp** |
| same_ticker AND same_section in top-5 | 0.734 | 0.741 | **+0.7 pp** |

By these signals, recursive chunking is **at least as good** as naive. The locked numbers above are kept verbatim for the immutable record.

## Why the small RAGAS regressions (the real signal)

`context_recall` regressed -1.4 pp and `answer_relevancy` -3.5 pp. The likely cause:

- **+21.7% more chunks (4447 → 5412)** means the embedding index is denser. With more chunks, the embedding space is fragmented into more, smaller regions, and the same query can land on a slightly different neighborhood. This is a real cost of paragraph-aware chunking and would show up as a small recall regression.
- **+14.2% mean latency** is a direct consequence: more chunks → more cosine scores to compute → 1.2 s/Q slower. This is also why the cost is lower (-21.5%): RAGAS judge is doing less work because the top-5 are slightly more relevant on average.
- **Synthesis questions** in particular benefit from paragraph-aware chunks (less mid-sentence splitting), so the answer quality should improve there, which is consistent with the +11.1 pp content-based synthesis hit@5.

The regression is small enough to be either noise or a real effect; a follow-up with batched RAGAS judging (to reduce judge variance) would settle it. For now, exp_002 is a **marginal** change vs exp_001 by the trustworthy metrics.

## What this experiment actually teaches

1. **The locked chunk_id-based hit@5 metric is brittle** — it conflates "did retrieval find the right context?" with "does the eval set's source_chunk_id still exist in the index?". The first is a property of the system; the second is a property of the eval set + chunker pair. We need a content-anchored version going forward.
2. **Recursive chunking is roughly equivalent to naive on this dataset**, with mild evidence it helps section and synthesis questions. It's not a clear win, but it's not a clear loss either once the metric artifact is removed.
3. **The chunker dispatch wiring works**: `settings.chunker_strategy = "recursive"` selected the right chunker end-to-end (verified by the +21.7% n_chunks delta and the chunker=recursive metadata on every chunk). Future chunker experiments (exp_003 semantic, exp_004 structural, exp_005 late, exp_006 contextual) can plug in without further code changes.
4. **Recursion produces too many small chunks** for some sections (e.g., GS's 10-K has 632 recursive chunks vs an expected ~370). This suggests the `chunk_size=2000` / `chunk_overlap=200` budget is wrong for some filings — the 10-K's MD&A can have long single paragraphs that get split at the next separator (sentence level), which is fine, but if the text has many tiny paragraphs we get more, smaller chunks. A future experiment should investigate optimal `chunk_size` per section.

## Decisions for the next chunker experiments

- **Switch hit@5 and citation_accuracy to content-anchored versions** in the eval set v2 (or add a parallel `*_content` column) before running exp_003 onward. Otherwise every chunker change will look like a regression.
- **exp_003 (semantic chunking) is likely the most promising next step**, because the small synthesis regression here suggests structure alone isn't enough; we need chunking that respects semantic similarity between sentences, not just punctuation.
- **exp_004 (structural) should compare against the recursive result** with the corrected hit@5, not against the naive baseline.
